# RAG 知识库设计文档

> 项目编号：1.RAG知识库
> 日期：2026-08-25（2026-08-25 更新：接入方式改为 MCP Server）
> 状态：待评审（等待其余模块需求发完后统一评审）

## 1. 背景与目标

为 **agent** 提供企业知识库检索增强能力。输入为 PDF、Excel、邮件等多源异构文档，输出为**带出处标注**的回答，供 agent 在其工作流中引用。**agent 通过 MCP（Model Context Protocol）协议调用本知识库**：agent 侧既是 MCP Client 又是生成方，知识库侧以 MCP Server 暴露检索能力，回答的生成由 agent 的 LLM 完成，知识库负责给出带出处的高质量上下文。

核心质量目标（成功标准）：

| 目标 | 衡量方式 |
|------|----------|
| 表格结构不丢失 | 表格类问题（如「XX 型号的单价」）能正确命中行列关系 |
| 精确标识可检索 | 产品型号、合同编号等精确值召回准确（不靠向量猜） |
| 版本正确 | 默认只检索当前生效版本，不把旧版本内容答出来 |
| 可追溯 | 回答每一句都能定位到来源 chunk 与原文位置 |
| 低幻觉 | 检索不到时明确说「没有找到」，绝不编造 |

## 2. 已确认决策

| 维度 | 决策 |
|------|------|
| 技术栈 | Python + 开源组件，内部部署 |
| 规模 | 千份级（500 – 10 万份文档） |
| 权限 | agent 全量访问，不做过滤；元数据保留部门/密级字段供将来启用 |
| 版本策略 | 只检索当前生效版本（按生效日期过滤），历史版本可显式指定版本号查询 |
| 算力 | 嵌入 + 重排模型本地部署；生成由 agent 自己的 LLM 完成（DeepSeek / 通义等），知识库不调生成模型 |
| 语言 | 以中文为主，兼顾中英混合内容 |
| 表格方案 | C：A+B 混合（表格转 Markdown 参与语义检索 + 独立表格切片供结构化查询） |
| 融合方式 | RRF（Reciprocal Rank Fusion）融合向量路与关键词路 |
| 接入方式 | MCP Server，同时支持 stdio（本地进程）与 streamable HTTP（远程服务）两种传输 |

## 3. 架构总览

系统分两条链路：

```
┌─────────────────────────── 离线索引流水线 ───────────────────────────┐
│  文档入库 → 解析(表格/图片/正文分离) → 清洗 → 切块+元数据 → 双路入库   │
│                                                    │                │
│                     ┌──────────────────────────────┼──────────┐     │
│                     ▼                              ▼          ▼     │
│              向量库(嵌入)                     关键词索引      表格索引 │
└────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────── 在线检索链路 ────────────────────────────┐
│  agent ──MCP──▶ 查询 → 向量召回 ╪ 关键词召回 → RRF 融合 → 重排        │
│        → 版本过滤 → 带出处上下文返回 agent（生成由 agent 的 LLM 完成） │
└─────────────────────────────────────────────────────────────────────┘
```

设计原则：**离线流水线与在线检索完全解耦**，各组件单向依赖、接口清晰，可独立测试与替换。MCP Server 是检索能力的唯一对外出口，只做检索与上下文组装，**不做生成**——生成交给 agent 自己的 LLM，避免知识库与 agent 的模型强耦合。

## 4. 离线索引流水线

### 4.1 解析层（多源异构）

统一解析接口 `DocumentParser.parse(path) -> ParsedDocument`，按文件类型分发：

| 类型 | 解析工具 | 说明 |
|------|----------|------|
| PDF | PyMuPDF + pdfplumber | 正文/图片/表格三路分离；表格用 pdfplumber 的表格检测 |
| Excel | openpyxl / pandas | 每个 sheet 单独处理，保留表头行与列结构 |
| 邮件 | 标准库 email + 附件解析 | 正文、发件人、主题、日期；附件递归走对应解析器 |

`ParsedDocument` 内部三通道：

- `tables[]`：结构化的行列数据（df 或 JSON）
- `images[]`：图片二进制 + 位置信息
- `text`：正文纯文本（保留阅读顺序）

### 4.2 清洗层

规则化清洗管线（可插拔规则器）：

1. 去页眉 / 页脚 / 页码 / 水印（按位置规则与内容模式）
2. 去空行、去乱码字符、统一全半角与换行
3. 合并跨页截断的段落
4. 表格归一化：空单元格补 `N/A`、合并单元格展开、统一列名

### 4.3 切块 + 元数据

**切块策略（语义边界优先）：**

- 以标题 / 段落 / 列表为天然边界切分，**禁止从句子中间断开**
- 相邻块保留 overlap（默认 10–15%，约 1–2 句），保证跨块上下文连续
- 块大小目标 300–500 token（中文），可按文档类型配置
- 超长表格不硬切：整表独立成块（见 4.5）

**元数据标签（每块必带）：**

| 字段 | 示例 | 用途 |
|------|------|------|
| `doc_type` | pdf / excel / email | 检索过滤、展示 |
| `department` | 销售部 | 预留权限（当前全量） |
| `version` | v2.3 | 版本管理 |
| `effective_date` | 2026-01-15 | 版本生效过滤 |
| `doc_id` / `chunk_id` | uuid | 溯源 |
| `source` | 文件名+页码/Sheet | 出处标注 |
| `table_id` | 仅表格块 | 关联结构化表格索引 |

### 4.4 表格处理（方案 C：A+B 混合）

每个表格**双份入库**：

- **A 路（语义）**：表格序列化为 Markdown 表格（`| 列1 | 列2 |`）作为正文块参与向量 + 关键词检索，保证「按语义问表」能召回
- **B 路（结构化）**：表格原始行列数据存独立表格索引（含表名、列名、表头摘要），支持按列名 / 表头 / 精确值查询，用于 agent 需要精确取值时

两条路通过 `table_id` 关联。检索到表格块时，回答可回连到结构化数据做精确核对。

### 4.5 图片处理

解析层抽取的图片走「OCR + 描述」双通道，保证图片信息可检索、可溯源：

- **OCR 通道**：扫描件/截图内文字用 PaddleOCR（中文）提取，作为图片的文本内容参与切块与检索
- **描述通道**（可选 v2）：对图表、示意图等无文字图片，由视觉模型生成一句话描述，作为图片块的文本参与检索
- **原始图片**：二进制存对象存储（MinIO），chunk 内保留 `image_id` 引用，回答引用图片块时可通过 `image_id` 取回原图

### 4.6 双路入库

- **向量库 + 关键词（Qdrant 单存储）**：一套 Qdrant 同时承载 dense 向量检索与 BM25 关键词检索（详见 4.6.1）。中文嵌入用 **BGE-M3**（1024 维，支持中文/英文/混合，且自带稀疏向量能力）
- **表格索引**：表格结构数据存 PostgreSQL + 全文检索
- **对象存储**：MinIO 存原始图片，chunk 经 `image_id` 引用

> BGE-M3 的稀疏向量与稠密向量可以双路同源，简化模型管理；但 BM25 关键词路仍保留，因为稀疏向量与 BM25 召回互补（BM25 对术语精确度更强）。

## 5. 在线检索链路

### 5.1 查询处理

- agent 原始问题 → 可选意图/实体识别（识别产品型号、合同号等精确实体，命中时提高关键词路权重）
- 查询改写（可选，v2）：同义扩展，仅当首轮召回不足时触发

### 5.2 双路召回

- **向量路**：query 嵌入 → 向量库 top-K 召回（K=50）
- **关键词路**：query 经中文分词 → Qdrant BM25 召回 top-K（K=50）
- 两路并行执行，超时与失败互不影响（一路挂了另一路仍可用）

### 5.3 RRF 融合

按排名倒数融合两路结果：

```
score(d) = Σ 1 / (k + rank_i(d))，k 默认 60
```

无需调权重，对两路分数尺度不敏感。融合后取 top-N（N=20）送重排。

### 5.4 重排

本地部署 **bge-reranker-v2-m3**（中文 + 多语言重排）。对 top-N 逐条打分精排，取 top-M（M=5–8）进上下文。

### 5.5 版本过滤

两个位置双重保险：

1. **检索前**（索引侧）：向量库检索时用 `effective_date` 过滤条件排除已过期版本；关键词检索加同样 filter
2. **检索后**（结果侧）：对同一 `doc_id` 的多版本结果按生效日期取最新，去重

### 5.6 上下文组装

- 按重排分数排列 chunk，拼装为**带出处标记的结构化上下文**（JSON 或带引用的文本）
- 每个 chunk 携带 `source` 元数据（文件名 + 页码 / Sheet + 块号），作为出处引用凭证
- 组装完成的上下文作为 MCP 工具返回结果交付给 agent，由 agent 的 LLM 生成回答

### 5.7 MCP 接口设计

知识库以 MCP Server 暴露检索能力，工具集如下：

| 工具名 | 用途 | 输入 | 输出 |
|--------|------|------|------|
| `search` | 主检索：双路召回 → RRF → 重排 → 版本过滤 | `query`（必填）、`top_k`（默认 5）、`version`（可选，指定版本号查历史）、`department`（可选，预留过滤） | 带出处标注的上下文列表（chunk 文本 + source 元数据 + 重排分数） |
| `retrieve_table` | 结构化表格精确查询（B 路） | `table_id` 或 `query` + `columns`（可选列名） | 表格行列数据（JSON） |
| `get_document` | 取原文块 / 图片原图 | `chunk_id` 或 `image_id` | 原文 / 图片二进制（图片走 object store） |
| `list_versions` | 查询某文档的版本历史 | `doc_id` | 版本列表（版本号 + 生效日期 + 状态） |

**传输**：同一套业务逻辑同时挂 stdio 与 streamable HTTP 两个 transport（用 MCP Python SDK 的 `FastMCP` 实现，`mcp.run(transport="stdio"|"http")` 或同时暴露）。

**工具规范要求（agent 侧防幻觉的关键）**：

- 每个返回 chunk 必须带 `source` 字段，且 `search` 的返回结构在 schema 中**固定包含出处字段**，防止 agent 遗漏引用
- `search` 无结果时返回空列表 + `empty_reason`（如「版本已过期」），agent 据此走「没有找到」分支

## 6. 生成侧防幻觉规范

生成由 **agent 自己的 LLM** 完成，知识库不调用生成模型。因此防幻觉约束拆为两层：

### 6.1 知识库侧（硬性保证，MCP 层）

1. 返回的上下文**只含检索到的真实 chunk**，每个 chunk 强制携带 `source` 元数据（schema 校验，缺 source 的 chunk 不允许返回）
2. 检索无结果时返回空上下文 + 明确原因，不填充任何猜测内容
3. 版本过滤保证返回的是当前生效版本内容

### 6.2 agent 侧（Prompt 模板约定）

知识库交付时附送一份**agent Prompt 模板**（系统提示词），约定三条不可违背规则，agent 接入方必须采用：

1. **只依据检索内容回答**：不得使用检索内容之外的知识；检索内容不足时，宁可说「没有找到」，不得推测或编造
2. **明确拒绝**：问题超出知识库范围或检索无结果时，直接回答「知识库中没有找到相关内容」
3. **逐句标注出处**：回答的每一句（或每个事实点）后标注来源 `[来源：文件名·页码/Sheet·块号]`；无法确定出处的表述不得出现

### 6.3 出处校验（可选，v2）

agent 生成回答后，可在 agent 侧对回答中每个出处引用做后置校验：引用块确在 `search` 返回的上下文中，防止 LLM 编造来源。

## 7. 数据流（完整时序）

```
入库:
  文件 → [解析] → ParsedDocument(表格/图片/正文)
       → [清洗] → 干净文本+表格
       → [切块] → chunks(含 overlap + 元数据)
       → [嵌入] BGE-M3 → 向量库 upsert
       → [关键词] → Qdrant BM25 index
       → [表格] → 表格索引 + Markdown 表入库

问答:
  agent --MCP--> [双路召回] 向量+BM25
             → [RRF] → top-20
             → [重排] bge-reranker → top-5~8
             → [版本过滤] → 当前生效版本
             → [上下文组装] → 带出处上下文返回 agent
             → [agent LLM 生成] → 带出处回答
```

## 8. 错误处理

| 场景 | 处理 |
|------|------|
| 解析失败（损坏 PDF 等） | 记录失败原因与文件，隔离该文档，不阻塞流水线其余文档；提供重试与人工标记 |
| OCR/图片无内容 | 图片抽取为空时记日志，不影响文本索引 |
| 检索两路都无结果 | 返回空上下文 + `empty_reason`，agent 按 Prompt 约定走「没有找到」分支 |
| 单路检索超时/失败 | 降级为另一路结果，记录告警 |
| 重排模型不可用 | 跳过重排，直接用 RRF 融合结果 |
| 版本冲突（生效日期重叠） | 取生效日期最新者，冲突记录进日志供人工核查 |

## 9. 测试策略

### 9.1 单元测试

- 切块边界：句子不被截断、overlap 长度符合配置
- 清洗规则：页眉页脚去除、乱码清理、跨页段落合并
- 表格序列化：Markdown 往返转换与结构保持

### 9.2 检索评测（离线评测集）

- 构造 50–100 条典型问答对（含表格问题、型号/合同号精确问题、版本问题）
- 指标：Recall@K、MRR、命中率（gold chunk 是否进入 top-5）
- 版本问题专项：确认旧版本不进 top 结果

### 9.3 端到端

- 问答质量抽样评测 + 出处可验证性检查（引用块确在上下文中）
- 幻觉专项：用知识库外问题测试，验证「没有找到」分支触发

### 9.4 MCP 接口测试

- 双传输连通性：stdio 与 streamable HTTP 各自拉起 server，工具能正常调用
- 工具 schema 校验：`search` 返回的每个 chunk 必须含 `source` 字段（缺字段即测试失败）
- 工具行为：`retrieve_table` 精确取数、`get_document` 取回原文/图片、`list_versions` 版本历史正确
- 空结果：无命中时返回空列表 + `empty_reason`，符合 agent 约定

## 10. 预留与扩展

- **权限**：元数据已含 `department` / 密级字段，检索链路预留 filter 参数；`search` 工具已预留 `department` 入参，将来按 agent 身份注入即可启用
- **增量索引**：流水线按 `doc_id + version` 幂等，支持增量入库与定时全量校验
- **查询改写**：v2 可选，仅首轮召回不足时启用
- **存储扩容**：Qdrant 单机起步，规模增长后平滑扩分布式（Qdrant 原生支持）
- **更多 MCP 工具**：v2 可按需扩展（如 `upload_document` 让 agent 直接入库、`list_documents` 浏览目录）

### 4.6.1 存储选型落地（Qdrant 单存储）

- 向量库：Qdrant（`Collection` 存 dense 向量，BGE-M3 1024 维）
- 关键词：Qdrant 的 BM25 稀疏检索能力（`sparse vector` 或全文索引），query 分词后走 Qdrant 召回
- 表格索引：PostgreSQL（表格结构数据 + 全文检索），经 `table_id` 关联
- 对象存储：MinIO 存原始图片

> 若 Qdrant BM25 在千份级+中文分词下效果不达标，备选回退方案为引入 ES 仅做关键词路（架构不变，仅替换检索实现），此决策点留待检索评测（9.2）数据支撑。
